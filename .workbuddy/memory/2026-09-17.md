## 三项缺口一起闭环（批次九十四：定价三出口 + 商税补面）

用户指示「一起调整」，把上面三项一并修掉。

### 改动
- **`scripts/sim/Goods.cs`**：新增 `FillRateOf`（整仓占用率）、`FactorOf`（定价用倍率，容量≤0 取平价防误判缺货）、`RetailPrice`（基价×1.5×库存倍率，家庭零买）、`BuyerPrice`（基价×库存倍率，铺面/工坊买方议价）、`Scale`（四舍五入取整 + 保底 1 文）。
- **`scripts/core/GameState.cs`**：新增 `PayFromBuildingTaxed(b, to, goodsValue, taxRate)`——买方为建筑的代扣商税结算。**关键设计**：先按含税总额 `PayFromBuilding` 付给卖方，再从卖方 `TakeFromFamily` 收回税款入官库。恒等式「买方出资 gross = 卖方所得 net + 官库税收 tax」天然守恒；若改成「买方只付净额 + 另向买方征税」，官营买方会变成官库自己给自己交税（收付相抵形同无税）。买方实付不足按比例缩放，净得 <1 文时免征。
- **`scripts/sim/GoodsSystem.cs`**：`BuyGoods` 改为逐铺现算单价、逐铺扣钱（各卖家库存不同价，原来的「开场估一个统一可买量」与此天然冲突）；售货款末位雇工收余数（原来 `pay/人数` 平摊丢余数）。
- **`scripts/agents/CitizenAgent.cs`**：`FindGoodsSource` 逐候选铺按 `RetailPrice` 判可买性；`Shopping` 按 `_supplyBuildingId >= 0` 分档（工坊补料=批发价、家庭补货=零售价，后者与自动购粮同价）；`Hauling`（工坊成品交商铺）与 `SellPack`（铺面收居民货）改走 `BuyerPrice` + `PayFromBuildingTaxed`。
- **`scripts/ui/InspectPanel.cs`**：储存区显示占用率与定价档位（平价/偏高折价/满仓折价/缺货溢价）；生产需求区区分「收价」与「零售」。
- **文档**：`specs/ECONOMY.md` 补 §4 定价三出口（含倍率表）与商税两征法、§9 拆成「已闭环/仍待办」、§10 改成实际 `BasePrice` 表并标注设计锚点（烧饼≈1文）与实现值（15文）不平；`CODEMAP.md`、`CHANGELOG.md`（批次九十四条目）同步。

### 结论/坑
- 「同货不同价」不是简单统一数值就完事：家庭自动购粮是**被动零买**（断炊才买，吃零售价合理），工坊补料是**生产性整担进货**（批发价合理）。所以不是把两个数改成一样，而是把「零售/批发」这条两档规则**显式化并集中到一个出口**。
- **店坊雇工≈合伙人**（写进文档 §4 要点与 §5.1）：`grown` 店坊雇工既是跑腿垫付进料货款的人，也是售货分账的收款人——不是 bug，是既有设计，别再误判成「员工替老板出钱」的泄漏。
- 顺手修的余数泄漏：`BuyGoods` 里 `pay / staff.Count` 逐人平摊，除不尽余数凭空消失（余数为 0 时看不出来，pay=100/3 人时每笔丢 1 文）。

## 物品时效系统（批次九十五第一批：双时间轴内核 + 货品属性分批存储）

用户需求：为所有物品引入状态系统并把房屋、道路一并纳入、复用同一套命名与机制；定义新鲜度（软轴三阶段）与有效期（硬轴）两种阈值，阈值受外界环境影响并支持部分回滚；物品按属性分批存储，不再简单数量叠加。**用户要求先研究现有实现、沟通确认方案、最后再实现**——故先做了一轮调研+方案确认（4 个 AskUserQuestion），再动工。

### 调研发现（写方案时的依据）
现有**五套互不相通的衰减实现**，且统一基座 `Obj` 抽象基类其实早已存在（`BuildingInstance`/`PlantObj`/`AnimalObj`/`ItemPileObj` 都是其子类）：
| 实体 | 现有字段 | 已实现 | 缺 |
|:---|:---|:---|:---|
| 货品 `GoodsStack` | `AgeDays` | 只计龄、零效果 | 两轴全缺 |
| 房屋 `BuildingInstance` | `Condition` 0~100 | 旬衰减→修缮回血→归零坍塌 | 已有硬轴、缺软轴 |
| 植物 `PlantObj` | `Hp`+`IdleDays` | 砍伐扣血→闲置延迟后逐日回血 | **"延迟+回滚"现成范例** |
| 人 `Citizen` | `Health` 100+`AgeMonths` | 老化、老死 | 未接入 |
| 动物 `AnimalObj` | `AgeMonths` | 增龄、减员 | 同上 |
| 道路 | 无 | `Cell.HasRoad/RoadKind/LaneOwnerId` 三件套 | 全缺（**`Cell` 是 struct + 100 万格 dense 数组，不能加字段，必须稀疏字典**） |

另：`Goods.Scrap`（废料，燃料类）已存在 → "硬轴归零变垃圾"的现成落点；`Obj.Extra`（`Dictionary<string,string>`）是 mod 扩展位。

### 用户确认的四个设计决策
1. 物品粒度：**按属性分批**（不是每件一实例）。关键论据：`Amount` 是**连续量**（口粮 0.2333 份/人/旬），"每件一实例"在现有数据模型下语义不成立。
2. 回滚语义：用户给了两个例子，揭示**第三种语义——带代价的恢复**：「饭菜回锅后恢复新鲜度，但减少保质期/后续流失更快」「柴薪久了热量降低，烘干后恢复热量」。即每次翻新透支未来 → `RenewCount` 驱动复合惩罚。
3. 两轴**独立并存**（非单轴三阶段）。
4. 环境修正要**可注册接口**，"包括但不限于露天室内季节、还有存储方式以及回锅情景"。

### 实现要点（批次①，已完成并 0 警告 0 错误）
- 新增 `configs/TimelinessConfig.cs` + `sim/timeliness/{TimedState,TimedModifier,TimedRules,TimedRegistry,TimelinessSystem}.cs` + `specs/TIMELINESS.md`。
- **三字段模型**：`Fresh`/`UsedLifespan`/`RenewCount`；`Span` 与速率**全部现算**（环境实时改阈值，存派生量会失真且季节切换要全城改写）。
- **效果打折 = 消耗时有效量折算** `有效量 = 取用量 × EffectOf(Fresh)`，一处改动同时覆盖粮食与柴薪（`Inventory.ConsumeEffective`，接入 `GoodsSystem` 口粮/柴薪/饮水/分级需求）。
- **环境修正可注册**：`ITimedModifier` 乘算累积、基准"露天+春季"；内置位置（有顶 ×0.45速率/×1.6寿限）、季节、临水三源。
- **分批合并键不含环境**：`SameBand` = 鲜度档 + **已耗寿限档** + 翻新次数。两个刻意选择——① 用"已耗"而非"剩余"（剩余是派生量，会随搬家变，当键会把同批货拆开）；② 不含环境标签，因为衰减速率只取决于当前储存点与季节，差异会**自然沉淀到 `Fresh` 数值**里，两天后自动落档分开，且避免"季节一变全城重新分批"。
- **搬运保状态**：改 `GameState.PickupPile`/`ClaimCellForBuilding`、`CitizenAgent.Hauling`/`SellPack`、`Stall.TickTrade`、`VisitorSystem` 进口，走 `TakeBatch`→`StoreBatch`（否则"露天搬进仓库"会在半路丢失损耗）。
- 面板逐批显示「鲜 78% / 渐损 45% / 已失效」+ 剩余天数 + 翻新次数；剩余按当前环境现算，搬进仓房能立刻看到数字变长（阈值回滚的可见体现）。

### 两个踩到的坑（已写入 CHANGELOG）
- **`const bool` 配置开关会被编译器折叠**，使 `if (!Enabled) return;` 的关闭分支被判"不可达代码"（CS0162 ×3）→ 改 `static readonly bool`。
- **`GoodsStack.Fresh` 的字段初始化器 `= 100f` 不可省**：旧存档缺该字段时反序列化保留 100；若默认 0，全部库存会瞬间被判"已失效"。

### 用户举例揭示的设计要点（值得记住）
- 「回锅」不是简单回血，而是**用总寿命换当下品质**：恢复鲜度但 `寿限 ×0.65^n`、`衰减 ×1.8^n`，递减收益自然涌现，**无需额外规则禁止无限回锅**。
- 「柴薪热量降低」说明软轴的效果打折要落到**消耗端折算**（湿柴要烧双份），而不是只做个数值标签。

### 时间尺度（本次校准，后续调数值必看）
**1 游戏日 = 20 秒现实**（1 旬 = 3 日 = 60 秒、1 月 = 3 分钟、1 年 = 36 分钟）。故「易腐品 15 日」≈ 现实 5 分钟——既来得及反应也够紧迫。初稿基线：野味 10 日 / 烧饼 15 日 / 果品 24 日 / 粮食 120 日（硬轴 480）/ 柴薪 240（无硬轴）。未登记 `Baselines` 的货品一律不参与时效。

## 批次②：房屋 + 道路接入（同日续做）

### 房屋
- 硬轴：`BuildingInstance.UsedLifespan`（按 Category 给寿限：官署 14400 / 工商民居 7200 / 田块 3600 游戏日；天然、朝廷、王爷府豁免）。由 `TimelinessSystem.TickBuildings` 推进。
- 软轴：沿用既有 `Condition`（0~100，与货品同尺度同阶段语义），**仍由 MaintenanceSystem 驱动**——它有修缮匠与住户集资两条既有回滚通路，不搬家。
- **修缮即翻新**：新增 `RepairAccum`，累计修复量每满 100% 记一次大修 → `RenewCount++` → 与货品完全相同的 `寿限 ×0.65^n` 折扣，"老房子越修越难维持"自然成立。**用累计量而非逐次计数**——日常养护是逐旬小额回血，逐次计数会瞬间顶到上限、寿限直接归零。
- 两条坍塌路径统一由 `MaintenanceSystem.Collapse` 判定（软轴破败归零 / 硬轴寿限到寿）。刻意不把拆房放衰减器里，免得住户失所与业权清理散成两处。

### 道路
- 稀疏状态 `GameState.RoadStates`（`Dictionary<int, TimedState>`，键为格索引）。**不能进 `Cell`**——Cell 是 struct 且活在 100 万格 dense 数组里，加字段会让整图内存成倍增长；道路仅几千格，字典开销可忽略。
- 建档/清除挂在 `RegisterRoadCell` / `UnregisterRoadCell` 上 → 所有铺路、拆路、降级路径自动覆盖（核对过四处拆路点均已配对）。`UpgradeRoadCell` 升级路面时刷新路况（升级受 RoadRank 单向约束，不能反复升级刷寿命）。
- 双轴：软轴=路况（主 360 / 辅 240 / 小路 120 日）→ 移速 `0.55 + 0.45 × EffectOf`（下限防通行瘫痪），接入 `CitizenAgent` 与 `ForeignVisitor`；硬轴=寿限（主 720 / 辅 480 / 小路 240）→ `DegradeRoad` 降一级（主→辅→小路→冻结最差）。**刻意不拆路**：拆路会破坏玩家路网与"建筑临路"判定。
- **可见反馈**：路面顶点色按路况朝土褐插值（`ChunkGeometryBuilder.RoadWornColor`）。移速变化玩家察觉不到，颜色变暗发土一眼可见。
- **只在跨阶段门槛时广播 `CellChanged`**：逐日全标脏等于每天重建整张地图（路格数千）；退化为"阶段式视觉变化"后重建低频，且恰好与三阶段语义一致。

### 存档
- `BuildingSave` 加 `UsedLifespan`/`RenewCount`/`RepairAccum`；`MapSave` 加与 `RoadCells` 平行的 `RoadFresh`/`RoadUsed`。
- **读档顺序有坑**：道路状态必须在 `RegisterRoadCell` **之后**写回，否则被"新铺路面 = 全新状态"覆盖。
- **刻意不升 `FormatVersion`**（保持 25）：三个新增字段都有安全默认值（满鲜度 / 全新结构 / 无路况记录即全新路），旧档读入即"万物如新"，行为合理，不必让玩家存档作废。注释用「批次九十五：」而非「v26：」，避免与实际版本号冲突。
- 面板：建筑页显示「完好 78% 失修 · 大修 2 次 · 结构余 186 年」（剩余不足三年改用"日"）。

### 待办
道路尚无养护机制（修缮匠目前只修建筑），故寿限刻意设得长；养路并入批次④。

## 批次③：植物 + 动物 + 人接入（同日续做）

### 调研到的关键事实
- **人的 `Citizen.Health` 是死字段**：`LifeConfig` 注释自陈"当前健康恒满为中性，健康系统接入后自动生效"，但全项目**没有任何地方降低过 Health** → 死亡率放大系数 `HealthMortalityFactor(100)` 永远是常数 1.0，也是没接任何产出的纯摆设。
- **动物的"自然减员"与年龄无关**：`WildlifeSystem` 每月按 `NaturalDeathChance` 纯随机移除，`AgeMonths` 只涨不判死。
- **植物只有砍伤回血、没有寿限**：`Hp` + `IdleDays` 延迟自愈，无自然老死。

### 植物
- 软轴沿用既有 `Hp`（砍伐扣血 → 闲置延迟后逐日自愈）——这套"延迟+回滚"本就与统一机制同形，**不重写**。
- 新增 `VigorPercent = Hp / MaxHp × 100` 接入统一阶段与效果折算；**保留 Hp 绝对值**，以免抹掉"老树更耐砍"（MaxHp 随树龄增长）的既有玩法。
- 新增硬轴 `UsedLifespan`（10800 游戏日 = 300 游戏年）→ 到寿枯死倒伏，掉落木材（死木质次，出材减半：`MaxHp × WoodPerHp × 0.5`）。
- 效果落点：产果量 `FruitPerDay × VigorFactor`（树越被砍越歉收）。

### 动物
- 新增软轴 `Fresh`（体况 0~100），季节驱动：冬季 −1.8/日、其余 +0.42/日。
- **数值配比是关键**：年净 ≈ −4.9 点 → 从满值滑到下限约 15 游戏年，**恰好等于寿限（15 游戏年）**，于是"动物一生从肥壮走到羸弱"自然成立。若回复值调大（如 +0.9）体况会在春季就回满、全年贴着上限，季节波动形同虚设。
- 新增硬轴：年龄到寿老死，与既有随机减员**并存**（后者代表意外/天敌，保留种群不确定性）。
- 效果落点：繁育率 ×`BreedFactor`、猎获出肉 ×`YieldFactor`，两者都有下限——**避免体况归零导致种群自我灭绝**（这是接入时效系统时最容易玩死生态的坑）。

### 人
- `TickPeople` 推动 Health：断炊 −3/日、受冻 −2/日、温饱 +5/日（约 20 游戏日回满）。有损耗则只扣不回（饥寒交迫时不该还在变好）。
- **效果落点 `LaborFactor = 0.35 + 0.65 × EffectOf(Health)`**，接进两处：`GoodsSystem.TickMonth` 田间收获、`CraftingSystem` 工坊加工。两处都由"数人头"改为"算劳动当量"（人数 × 各自健康折算）——`CraftingSystem.CountWorkers` 因此改名为 `BuildLaborIndex` 并返回 `Dictionary<int, double>`。
- 硬轴沿用既有年龄（Gompertz 曲线 + 达最大寿数必亡）。
- 手感：**饥荒不再只扣兴致，而是直接削弱全城产能**（病农夫亩产低、病工匠出活少），形成迟滞但真实的恶性循环。

### 坑
- **`MathF` 没有 `Clamp` 重载**（只有 `Math.Clamp`）→ CS0117。`MathF.Max/Min/Pow` 存在，只有 Clamp 缺。
- `AnimalObj.Fresh` 的**字段初始化器 `= 100f` 不可省**（与 `GoodsStack.Fresh` 同理）：旧档缺该字段时保留满膘，否则全图动物瞬间被判"极瘦弱"、繁育率跌到下限量。

### 面板
村民页「健康 82（劳动 88%）」、树木页「茁壮/衰颓/濒枯 x%」、动物页「体况：肥壮 78%」——三者共用同一个 `StageLabel` 辅助（六类实体同一套阶段语义，标签构造也共用一处）。

## 批次④：恢复动作 + 操作入口 + NPC 自救 + 失效处置 + 道路养护（同日续做，四批收官）

### 恢复动作表（`TimelinessConfig.RenewSpecs`）
回锅（烧饼，耗柴薪 0.2/份）、重腌（腌货，耗精盐 0.1）、澄清（酒，无辅料）、烘干（柴薪，耗木炭 0.08）、晾晒（兽皮）、复晒（草药）。

**设计关键：恢复量是"拉回到固定值"而非"+N 点"**。因为"+N 点"可以让玩家无脑反复刷；"拉回到 85%"则第二次使用时鲜度本就没掉多少，拉到同一个值等于白费一次寿限折扣——递减收益自动生效，不需要额外规则。

### 执行入口（新增 `sim/timeliness/RenewAction.cs`）
`Apply`（恢复）/ `Salvage`（失效处置）/ `WorthRenewing`（NPC 判据）/ `SpecOf`。

⚠️ **最关键的实现细节：改完状态必须重新归档**。`SameBand` 的档位由鲜度档 + 已耗寿限档 + 翻新次数共同决定，翻新同时改了鲜度和翻新次数 → 档位变化。所以必须先从 `Stacks` 摘出旧批、再按新状态 `StoreForceBatch` 入库。**直接改 `GoodsStack` 的字段会让这批货赖在错误的档里**，后续合并与面板显示全部失真。

### 玩家入口
面板物品行尾挂 BBCode 链接 `[url=renew:货品id]回锅[/url]` / `[url=salvage:货品id]处置[/url]`，`OnMetaClicked` 加两个前缀就地执行，然后 `RefreshCurrent()` 重建当前页（建筑页或地面堆页）。
**复用既有 `[url=citizen:...]` + `MetaClicked` 机制，完全不动面板结构**——面板是只读 RichTextLabel，加按钮要大改，挂链接几乎零成本。

### NPC 自救（`TimelinessSystem.AutoRenew`）
每日替民居打理。触发线"鲜度 < 40 且翻新 < 2 次"——**居民不会不计后果地反复翻新把寿限耗光**（若不加这两道闸，NPC 会把每件食物翻到 `RenewMaxCount` 上限，寿限直接归零）。只对 `HousingCapacity > 0` 的民居生效；商铺货架与官仓廪留给玩家。

### 「失效后可作他用」的落点
`Salvage` 按 0.3 比例把已失效批次降级为 `Goods.Scrap`（废料，燃料类，可当柴烧）。硬轴归零时系统自动做同样的事（`ConvertToScrap`），`Salvage` 是让玩家/NPC **提前**出手腾仓容。

### 道路养护
`MaintenanceSystem.RepairOfficial` 里修缮匠修完建筑后若还有工量余量 → `RepairWorstRoad` 把全城路况最差的一格补到满。与"修最破的那一座"同策略：**均摊会让每条路都修不好**。跨阶段时才广播重建（与 TickRoads 同口径）。
这是批次②留下的待办（当时道路只老化无人养护，故寿限设得很长）。

### 坑
