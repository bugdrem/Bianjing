# 物品时效系统（Timeliness）

> 批次九十五起。六类实体（货品 / 房屋 / 道路 / 植物 / 动物 / 人）共用同一套时间阈值命名与机制。
> 调参唯一入口 `configs/TimelinessConfig.cs`；机制实现 `scripts/sim/timeliness/`。

---

## 1. 两条时间轴

| 轴 | 名称 | 语义 | 归零后果 |
|:---|:---|:---|:---|
| 软轴 | **新鲜度 Fresh**（0~100） | 品质衰减，物品仍在、仍可用 | 效果归零，**可作他用**（转化/降级/丢弃） |
| 硬轴 | **有效期 Lifespan** | 存在性倒计时 | **从世界移除**，或降级为废料 |

两轴**独立计时、独立存在**。粮食可以是「鲜度已掉到 40% 但仍能吃到第 480 日」。

### 软轴三阶段

| 阶段 | 阈值 | 效果折算 | UI 色 |
|:---|:---|:---|:---|
| 全效果 Full | Fresh ≥ 60 | 1.00 | 青绿 |
| 渐变衰减 Waning | 15 ≤ Fresh < 60 | 1.00 → 0.25 线性 | 琥珀 |
| 已失效 Spent | Fresh < 15 | 0.25 → 0 线性 | 赤 |

阈值在 `FreshFullThreshold` / `FreshWaneThreshold`，折算曲线在 `TimedRules.EffectOf`。

### 效果打折怎么落地

统一实现为**消耗时的有效量折算**：

```
有效量 = 实际取用量 × EffectOf(Fresh)
```

一处改动同时满足粮食与柴薪：鲜度 50% 的柴只能当半份烧（要烧双倍才够），鲜度归零的粮吃了不顶饱。
消耗路径见 `Inventory.ConsumeEffective`，接入点：`GoodsSystem` 的口粮 / 柴薪 / 饮水 / 分级需求。

折算系数 < 0.02 的批次**不参与正常消耗**（避免除零把取用量放大到无意义），
即"已失效"的实际含义是"不能再按原用途消耗"，而不是"物品消失了"。

## 2. 数据模型：只存三个客观量

```csharp
public struct TimedState
{
    public float Fresh;         // 软轴当前值 0~100
    public float UsedLifespan;  // 硬轴已耗天数（单调累积）
    public int   RenewCount;    // 翻新次数
}
```

**`Span` 与衰减速率都不存，全部现算**：

```
Span   = BaseSpan × Π(环境寿限倍率) × pow(RenewSpanPenalty, RenewCount)
Rate   = 100 / BaseFreshDays × Π(环境速率倍率) × pow(RenewRatePenalty, RenewCount)
剩余    = max(0, Span - UsedLifespan)      ← 必须夹紧
```

理由：环境会实时改变阈值。存派生量会在环境变化时失真，且被迫在每次季节切换时遍历全城改写。
现在只要环境一变，全城的剩余寿命**自动**跟着变，存档里只留"客观事实"。

货品的对应字段落在 `GoodsStack`（`Fresh` / `UsedLifespan` / `RenewCount`）。
⚠️ `GoodsStack.Fresh` 的**字段初始化器 `= 100f` 不可省**——旧存档缺该字段时反序列化会保留 100，
否则默认 0 会让全部库存瞬间被判成"已失效"。

`AgeDays` 保留为展示口径（累计存放时长，不受环境影响）：它只说"放了多久"，`Fresh` 才说"现在有多好"。

## 3. 环境修正：可注册的接口，不写死枚举

```csharp
public interface ITimedModifier
{
    string Id { get; }
    int Order { get; }                                  // 小者先应用
    bool Applies(in TimedContext ctx);                  // 该实体+该位置+该月是否命中
    void Apply(in TimedContext ctx, ref TimedRates rates);
}

public struct TimedRates
{
    public float FreshRate;     // 软轴衰减速率倍率
    public float LifespanSpan;  // 硬轴寿限阈值倍率
}
```

各修正源**乘算累积**，中性基准 1.0（露天 + 春季）。注册表见 `TimedRegistry`。

内置三源（批次①）：

| 修正源 | 命中条件 | 软轴速率 | 硬轴寿限 |
|:---|:---|:---|:---|
| `place` | 有顶室内 | ×0.45 | ×1.6 |
| | 无顶棚屋（NoRoof） | ×0.8 | ×1.15 |
| | 随身携带 | ×1.15 | ×0.95 |
| `season` | 夏 4-6 月 / 秋 7-9 月 / 冬 10-12 月 | ×1.6 / ×0.85 / ×0.55 | 不变 |
| `nearwater` | 四向邻格有水面 | ×1.35 | ×0.9 |

新增环境（地窖、熏房、冰鉴、地火炕）只需写一个实现类 + 一行 `TimedRegistry.Register`，衰减器与各实体接入处一行不改。

## 4. 合并与分档：环境不进键

用户在批次九十五明确要求「所有物品单独存储，只有属性相同且位于同一储存点的才支持合并与拆分」。

```
合并判定：SameBand(a, b)
  = 鲜度档相同  &&  已耗寿限档相同  &&  翻新次数相同
```

档宽：鲜度 10 点（10 档）、已耗寿限 30 游戏日。同档内按份数**加权平均**状态。

**两个刻意的设计选择：**

1. **用"已耗寿限"而非"剩余寿限"分档。** 剩余是派生量（受环境 `LifespanSpan` 影响，会随搬家而变），
   拿它当键会导致同一批货因环境变化被拆成两批。已耗寿限是客观事实，只增不减。

2. **合并键不含环境标签。** 衰减速率只取决于"当前储存点 + 当前季节"，同一储存点内所有物品共享同一套倍率，
   因此"露天坏得快、仓库坏得慢"这个差异会**自然沉淀到各自的 `Fresh` 数值里**——
   两天后它们自动落到不同鲜度档而分成两批，无需任何环境标记，
   也避免了"季节一变就要全城重新分批"的灾难。

取出默认**最差优先**（`WorstIndex`，先吃快坏的），搬运走 `TakeBatch` → `StoreBatch` 保状态。

## 5. 翻新：带代价的恢复

回锅、烘干、腌制等恢复动作**不是**简单的回血——每次翻新都透支这件东西的未来：

```
Fresh       ← min(100, Fresh + 动作的 FreshGain)
RenewCount  += 1        →  寿限 ×0.65^n、衰减速率 ×1.8^n
```

| 翻新次数 | 寿限剩余 | 衰减倍率 |
|:---|:---|:---|
| 1 | 65% | 1.8× |
| 2 | 42% | 3.24× |
| 3 | 27% | 5.83× |

递减收益自然涌现——不需要额外规则去禁止无限回锅。`RenewMaxCount = 6` 只是防数值下溢的保险。

**烧饼示例**（鲜度 15 日 / 保质期 45 日）：第 5 天回锅，鲜度从 37 跳到 90，
但衰减变为 1.8 倍、保质期缩到 29 日。**用总寿命换当下品质**，这正是设计意图。

**实现归属**：动作表见 `TimelinessConfig.RenewSpecs`（回锅 / 重腌 / 澄清 / 烘干 / 晾晒 / 复晒，各有辅料需求），
执行入口 `RenewAction.Apply`。

- **玩家侧**：面板物品行尾挂 `[url=renew:货品id]回锅[/url]` 链接，点击就地执行——复用既有的 BBCode `MetaClicked` 机制，不动面板结构。
- **NPC 侧**：`TimelinessSystem.AutoRenew` 每日替民居打理家务（把要坏的食物回锅、受潮的柴烘干）。只在**鲜度跌到 40 以下、且翻新未超 2 次**时动手——居民不会不计后果地反复翻新把自己的寿限耗光。只对有人住的民居生效（`HousingCapacity > 0`），商铺货架与官仓廪留给店主与玩家。

**执行时必须重新归档**：动作改完 `Fresh` 与 `RenewCount` 后，`SameBand` 的档位随之改变，
所以要先从 `Stacks` 摘出该批、再按新状态 `StoreForceBatch` 重新入库。
直接改字段会让它赖在错误的档里，后续合并与显示都会失真。

### 5.1 「失效后可作他用」

软轴进入失效段（Fresh &lt; 15）后，物品**仍在**，只是效果折算趋近 0、不能再按原用途消耗。
「作他用」由 `RenewAction.Salvage` 落地：**按 0.3 比例降级为 `Goods.Scrap`**（废料，燃料类货品，可当柴烧）。

硬轴寿限耗尽时系统会自动做同样的事（`TimelinessSystem.ConvertToScrap`）；
`Salvage` 是让玩家/NPC 提前出手，趁早腾出仓容。玩家侧同样挂在物品行的 `[url=salvage:]` 链接上。

## 6. 时间尺度校准

**1 游戏日 = 20 秒现实**（1 旬 = 3 日 = 60 秒，1 月 = 3 旬，1 年 = 36 旬 = 36 分钟，见 `TimeConfig`）。

所有阈值按此校准——「易腐品 15 日」≈ 现实 5 分钟，是玩家来得及反应也够紧迫的窗口。

| 类别 | 代表 | 软轴（游戏日） | 硬轴（游戏日） | 现实感受 |
|:---|:---|:---|:---|:---|
| 极易腐 | 野味 / 饮水 | 10 / 6 | 30 / 18 | 3 分钟内必须处理 |
| 易腐 | 烧饼 / 果品 / 兽皮 | 15 / 24 / 20 | 45 / 60 / 60 | 5~8 分钟 |
| 中期 | 草药 / 腌货 / 粮食 | 45 / 90 / 120 | 150 / 360 / 480 | 15~40 分钟 |
| 长期 | 柴薪 / 酒 / 木炭 | 240 / 300 / 600 | 无硬轴 | 80 分钟以上缓慢受潮 |
| 极稳 | 皮革 / 盐 / 铁器 / 成衣 | 900~1800 | 无硬轴 | 基本不会坏 |
| 不参与 | 矿石 / 书籍 / 废料 | — | — | 未登记基线即永不腐坏 |

未登记在 `Baselines` 的货品**一律不参与时效**——比逐项写"永不腐坏"更省事，
也避免新增货品时忘记登记导致莫名腐烂。

## 7. 六类实体接入映射

| 实体 | 软轴含义 | 效果打折落点 | 硬轴归零后果 | 翻新动作 | 状态 |
|:---|:---|:---|:---|:---|:---|
| **货品** | 新鲜度 / 燥度 | 消耗时有效量折算 | 转 `Scrap`（0.3 比例） | 回锅、烘干、腌制 | ✅ 批次① |
| **房屋** | 完好度（沿用 `Condition`，同 0~100、同阶段语义） | 修缮计入"大修"折损寿限 | 坍塌（`DemolishBuilding`） | 修缮 → 累计为大修 | ✅ 批次② |
| **道路** | 路况（影响移速） | 移速倍率（下限 0.55） | 降一级（主→辅→小路→冻结最差） | 降级即重修 | ✅ 批次② |
| **植物** | 生机（沿用 `Hp`，按上限归一化） | 产果量、出材 | 到寿枯死倒伏（掉木材） | 闲置自愈（既有） | ✅ 批次③ |
| **动物** | 体况（冬掉膘、春夏回膘） | 繁育率、猎获出肉量 | 年龄到寿老死 | 无 | ✅ 批次③ |
| **人** | 健康（沿用 `Health`，此前恒满而失效） | 劳动效率（田间收获与工坊加工） | 年龄（既有 Gompertz 曲线） | 温饱即回血 | ✅ 批次③ |

房屋与植物**已各自实现过一根轴**（`Condition`、`Hp` + `IdleDays` 延迟回血），
批次②③的统一工作是改名、补另一根轴、把衰减器抽成公共的——工作量集中在货品与道路这两处从零开始的。

**道路的特殊约束**：`Cell` 是 struct、活在 100 万格的密集数组里（`MapGrid`），**不能加字段**。
道路状态必须走稀疏字典（只存有路的几千格），存档在 `MapSave` 加一组与 `RoadCells` 平行的列表。

### 7.1 房屋（批次②）

| 项 | 实现 |
|:---|:---|
| 软轴 | `BuildingInstance.Condition`（沿用既有 0~100 完好度），阶段语义与货品一致。仍由 `MaintenanceSystem` 驱动——它有修缮匠与住户集资两条既有的回滚通路，不必搬家 |
| 硬轴 | 新增 `UsedLifespan`（游戏日累积）。寿限按 Category：官署 14400 / 工商民居 7200 / 田块 3600；天然建筑、朝廷机构、王爷府豁免（与既有"不老化"口径一致） |
| 翻新 | **修缮即翻新**：累计修复量每满 100% 记一次大修（`RenewCount++`），驱动与货品完全相同的 `寿限 ×0.65^n` 折扣 |
| 坍塌 | 两条路径统一由 `MaintenanceSystem.Collapse` 判定：软轴破败归零（无人修缮）或硬轴寿限到寿。**不把拆房逻辑放到衰减器里**，免得住户失所、业权清理等收尾散成两处 |
| UI | 面板显示「完好 78% 失修 · 大修 2 次 · 结构余 186 年」；剩余不足三年改用"日"（对"还剩 0.4 年"没有实感） |

用**累计修复量进位**而非"每次修缮都计数"是关键：日常养护是逐旬小额回血，逐次计数会把 `RenewCount` 瞬间顶到上限、寿限直接归零。

### 7.2 道路（批次②）

| 项 | 实现 |
|:---|:---|
| 存储 | `GameState.RoadStates`（`Dictionary<int, TimedState>`，键为格索引，通常仅几千条） |
| 生命周期 | 随 `RegisterRoadCell` / `UnregisterRoadCell` 建档与清除——所有铺路、拆路、降级路径自动覆盖，无需逐处补 |
| 软轴 | 路况按路种基线衰减（主 360 日 / 辅 240 / 小路 120），叠加临水与季节修正 → 移速倍率 `0.55 + 0.45 × EffectOf(Fresh)` |
| 硬轴 | 寿限（主 720 / 辅 480 / 小路 240）→ `DegradeRoad` 降一级；降级即复位为全新路况并重新起算 |
| 不拆除 | 刻意不拆路：拆路会破坏玩家路网与"建筑临路"判定，代价远大于收益。"变成纯粹垃圾"由"还能走但极慢"表达 |
| 视觉 | 路面顶点色按路况朝土褐插值（`ChunkGeometryBuilder.RoadWornColor`）——移速变化玩家未必察觉，颜色变暗发土一眼可见 |
| 重建 | 仅在**跨阶段门槛**时广播 `CellChanged`。逐日全标脏等于每天重建整张地图；退化为"阶段式视觉变化"后重建低频，且恰好与三阶段语义一致 |

已知待办：**道路尚无养护机制**（修缮匠目前只修建筑），故寿限刻意设得长；养路并入批次④与恢复动作一起做。

### 7.3 植物（批次③）

| 项 | 实现 |
|:---|:---|
| 软轴 | 沿用既有 `Hp`（砍伐扣血 → 闲置 `RegenDelayDays` 后逐日自愈）。这套"延迟后回滚"本就与统一机制同形，**不重写** |
| 归一化 | 新增 `VigorPercent`（= Hp / MaxHp × 100）接入统一阶段判定与效果折算。**保留 Hp 的绝对值**——"老树更耐砍"（MaxHp 随树龄增长）是既有玩法，不该被归一化抹掉 |
| 硬轴 | 新增 `UsedLifespan`（10800 游戏日 = 300 游戏年）。到寿枯死倒伏，掉落木材（死木质次，出材减半） |
| 效果落点 | 产果量 `FruitPerDay × VigorFactor`：树越被砍越歉收 |

### 7.4 动物（批次③）

| 项 | 实现 |
|:---|:---|
| 软轴 | 新增 `Fresh`（体况 0~100），季节驱动：冬季掉膘、其余季节回膘 |
| 数值配比 | 冬季 −1.8/日、其余 +0.42/日 → 年净 ≈ −4.9，从满值滑到下限约 **15 游戏年**，恰好等于寿限：**动物一生就是从肥壮走到羸弱**，无需额外规则 |
| 硬轴 | 新增年龄寿限（15 游戏年）。与既有"随机自然减员"**并存**——后者代表意外与天敌，让种群有不确定性；寿限保证个体不会永生 |
| 效果落点 | 繁育率 `BreedChance × BreedFactor`；猎获出肉 `LoadUnits × YieldFactor`。两者都有下限，避免体况归零导致**种群自我灭绝** |

⚠️ `AnimalObj.Fresh` 的字段初始化器 `= 100f` 不可省（同 `GoodsStack.Fresh`）：旧档缺该字段时保留满膘，否则全图动物瞬间被判成极瘦弱。

### 7.5 人（批次③）

| 项 | 实现 |
|:---|:---|
| 软轴 | 沿用既有 `Citizen.Health`。**此前恒为 100**——`LifeConfig` 注释自陈"健康系统接入后自动生效"，但全项目没有任何地方降低过它，于是死亡率放大系数永远是 1.0 |
| 衰减与回滚 | 断炊 −3/日、受冻 −2/日；温饱时 +5/日（约 20 游戏日回满）。推进见 `TimelinessSystem.TickPeople` |
| 效果落点 | `LaborFactor = 0.35 + 0.65 × EffectOf(Health)`，落到**田间收获**（`GoodsSystem.TickMonth`，按劳动当量而非人头数）与**工坊加工**（`CraftingSystem` 同上） |
| 硬轴 | 沿用既有年龄（Gompertz 死亡率曲线 + 达最大寿数必亡），无需新建 |

这是三者中改动最有实感的一处：**饥荒不再只扣兴致，而是直接削弱全城产能**——病弱的农夫亩产低、病弱的工匠出活少，形成一个迟滞但真实的恶性循环。

### 8.1 已知限制与待办

- **配方系统不认识物品状态**：`Goods.Recipes` 按 `goodsId` 索引，不做状态条件判定。
  故「变质的粮拿去堆肥」目前通过降级为 `Scrap`（燃料类货品，天然可作他用）实现；
  若要做「鲜度 &lt; 15 的粮食 → 肥料」这类**指定产出的配方**，需要给配方加状态条件。
- **加工输入未按鲜度折算**：`CraftingSystem` 取原料走普通取出，陈粮酿酒与新粮同产率。
- **售价未按鲜度折算**：`Goods.RetailPrice` / `BuyerPrice` 只吃库存联动倍率，不吃鲜度——
  现实中陈粮该卖得便宜。引入后需与库存倍率叠加，注意别把两者相乘得过头。
- **地面堆的操作入口已支持，但访客行囊不支持**（访客不打开面板）。
- **搬运状态为近似**：跨批搬运时状态按取出量加权混合（单批场景精确无损）。
