# 物品时效系统（Timeliness）

> 批次九十五起。六类实体（货品 / 房屋 / 道路 / 植物 / 动物 / 人）共用同一套时间阈值命名与机制。
> 调参唯一入口 `configs/TimelinessConfig.cs`；机制实现 `scripts/sim/timeliness/`。

---

## 1. 两条时间轴

| 轴 | 名称 | 语义 | 归零后果 |
|:---|:---|:---|:---|
| 软轴 | **新鲜度 Fresh**（0~100） | 品质衰减，物品仍在、仍可用 | 效果归零，**可作他用**（转化/降级/丢弃） |
| 硬轴 | **有效期 Lifespan** | 存在性倒计时 | **从世界移除**，或降级为废料 |

两轴**独立计时、独立存在**。粮食可以是「鲜度已掉到 40% 但仍能吃到第 480 日」。

### 软轴三阶段

| 阶段 | 阈值 | 效果折算 | UI 色 |
|:---|:---|:---|:---|
| 全效果 Full | Fresh ≥ 60 | 1.00 | 青绿 |
| 渐变衰减 Waning | 15 ≤ Fresh < 60 | 1.00 → 0.25 线性 | 琥珀 |
| 已失效 Spent | Fresh < 15 | 0.25 → 0 线性 | 赤 |

阈值在 `FreshFullThreshold` / `FreshWaneThreshold`，折算曲线在 `TimedRules.EffectOf`。

### 效果打折怎么落地

统一实现为**消耗时的有效量折算**：

```
有效量 = 实际取用量 × EffectOf(Fresh)
```

一处改动同时满足粮食与柴薪：鲜度 50% 的柴只能当半份烧（要烧双倍才够），鲜度归零的粮吃了不顶饱。
消耗路径见 `Inventory.ConsumeEffective`，接入点：`GoodsSystem` 的口粮 / 柴薪 / 饮水 / 分级需求。

折算系数 < 0.02 的批次**不参与正常消耗**（避免除零把取用量放大到无意义），
即"已失效"的实际含义是"不能再按原用途消耗"，而不是"物品消失了"。

## 2. 数据模型：只存三个客观量

```csharp
public struct TimedState
{
    public float Fresh;         // 软轴当前值 0~100
    public float UsedLifespan;  // 硬轴已耗天数（单调累积）
    public int   RenewCount;    // 翻新次数
}
```

**`Span` 与衰减速率都不存，全部现算**：

```
Span   = BaseSpan × Π(环境寿限倍率) × pow(RenewSpanPenalty, RenewCount)
Rate   = 100 / BaseFreshDays × Π(环境速率倍率) × pow(RenewRatePenalty, RenewCount)
剩余    = max(0, Span - UsedLifespan)      ← 必须夹紧
```

理由：环境会实时改变阈值。存派生量会在环境变化时失真，且被迫在每次季节切换时遍历全城改写。
现在只要环境一变，全城的剩余寿命**自动**跟着变，存档里只留"客观事实"。

货品的对应字段落在 `GoodsStack`（`Fresh` / `UsedLifespan` / `RenewCount`）。
⚠️ `GoodsStack.Fresh` 的**字段初始化器 `= 100f` 不可省**——旧存档缺该字段时反序列化会保留 100，
否则默认 0 会让全部库存瞬间被判成"已失效"。

`AgeDays` 保留为展示口径（累计存放时长，不受环境影响）：它只说"放了多久"，`Fresh` 才说"现在有多好"。

## 3. 环境修正：可注册的接口，不写死枚举

```csharp
public interface ITimedModifier
{
    string Id { get; }
    int Order { get; }                                  // 小者先应用
    bool Applies(in TimedContext ctx);                  // 该实体+该位置+该月是否命中
    void Apply(in TimedContext ctx, ref TimedRates rates);
}

public struct TimedRates
{
    public float FreshRate;     // 软轴衰减速率倍率
    public float LifespanSpan;  // 硬轴寿限阈值倍率
}
```

各修正源**乘算累积**，中性基准 1.0（露天 + 春季）。注册表见 `TimedRegistry`。

内置三源（批次①）：

| 修正源 | 命中条件 | 软轴速率 | 硬轴寿限 |
|:---|:---|:---|:---|
| `place` | 有顶室内 | ×0.45 | ×1.6 |
| | 无顶棚屋（NoRoof） | ×0.8 | ×1.15 |
| | 随身携带 | ×1.15 | ×0.95 |
| `season` | 夏 4-6 月 / 秋 7-9 月 / 冬 10-12 月 | ×1.6 / ×0.85 / ×0.55 | 不变 |
| `nearwater` | 四向邻格有水面 | ×1.35 | ×0.9 |

新增环境（地窖、熏房、冰鉴、地火炕）只需写一个实现类 + 一行 `TimedRegistry.Register`，衰减器与各实体接入处一行不改。

## 4. 合并与分档：环境不进键

用户在批次九十五明确要求「所有物品单独存储，只有属性相同且位于同一储存点的才支持合并与拆分」。

```
合并判定：SameBand(a, b)
  = 鲜度档相同  &&  已耗寿限档相同  &&  翻新次数相同
```

档宽：鲜度 10 点（10 档）、已耗寿限 30 游戏日。同档内按份数**加权平均**状态。

**两个刻意的设计选择：**

1. **用"已耗寿限"而非"剩余寿限"分档。** 剩余是派生量（受环境 `LifespanSpan` 影响，会随搬家而变），
   拿它当键会导致同一批货因环境变化被拆成两批。已耗寿限是客观事实，只增不减。

2. **合并键不含环境标签。** 衰减速率只取决于"当前储存点 + 当前季节"，同一储存点内所有物品共享同一套倍率，
   因此"露天坏得快、仓库坏得慢"这个差异会**自然沉淀到各自的 `Fresh` 数值里**——
   两天后它们自动落到不同鲜度档而分成两批，无需任何环境标记，
   也避免了"季节一变就要全城重新分批"的灾难。

取出默认**最差优先**（`WorstIndex`，先吃快坏的），搬运走 `TakeBatch` → `StoreBatch` 保状态。

## 5. 翻新：带代价的恢复

回锅、烘干、腌制等恢复动作**不是**简单的回血——每次翻新都透支这件东西的未来：

```
Fresh       ← min(100, Fresh + 动作的 FreshGain)
RenewCount  += 1        →  寿限 ×0.65^n、衰减速率 ×1.8^n
```

| 翻新次数 | 寿限剩余 | 衰减倍率 |
|:---|:---|:---|
| 1 | 65% | 1.8× |
| 2 | 42% | 3.24× |
| 3 | 27% | 5.83× |

递减收益自然涌现——不需要额外规则去禁止无限回锅。`RenewMaxCount = 6` 只是防数值下溢的保险。

**烧饼示例**（鲜度 15 日 / 保质期 45 日）：第 5 天回锅，鲜度从 37 跳到 90，
但衰减变为 1.8 倍、保质期缩到 29 日。**用总寿命换当下品质**，这正是设计意图。

实现归属：动作表与 UI 入口在批次④。

## 6. 时间尺度校准

**1 游戏日 = 20 秒现实**（1 旬 = 3 日 = 60 秒，1 月 = 3 旬，1 年 = 36 旬 = 36 分钟，见 `TimeConfig`）。

所有阈值按此校准——「易腐品 15 日」≈ 现实 5 分钟，是玩家来得及反应也够紧迫的窗口。

| 类别 | 代表 | 软轴（游戏日） | 硬轴（游戏日） | 现实感受 |
|:---|:---|:---|:---|:---|
| 极易腐 | 野味 / 饮水 | 10 / 6 | 30 / 18 | 3 分钟内必须处理 |
| 易腐 | 烧饼 / 果品 / 兽皮 | 15 / 24 / 20 | 45 / 60 / 60 | 5~8 分钟 |
| 中期 | 草药 / 腌货 / 粮食 | 45 / 90 / 120 | 150 / 360 / 480 | 15~40 分钟 |
| 长期 | 柴薪 / 酒 / 木炭 | 240 / 300 / 600 | 无硬轴 | 80 分钟以上缓慢受潮 |
| 极稳 | 皮革 / 盐 / 铁器 / 成衣 | 900~1800 | 无硬轴 | 基本不会坏 |
| 不参与 | 矿石 / 书籍 / 废料 | — | — | 未登记基线即永不腐坏 |

未登记在 `Baselines` 的货品**一律不参与时效**——比逐项写"永不腐坏"更省事，
也避免新增货品时忘记登记导致莫名腐烂。

## 7. 六类实体接入映射

| 实体 | 软轴含义 | 效果打折落点 | 硬轴归零后果 | 翻新动作 | 状态 |
|:---|:---|:---|:---|:---|:---|
| **货品** | 新鲜度 / 燥度 | 消耗时有效量折算 | 转 `Scrap`（0.3 比例） | 回锅、烘干、腌制 | ✅ 批次① |
| **房屋** | 宜居度（沿用 `Condition`） | 吸引度、容纳效率 | 坍塌（现有 `DemolishBuilding`） | 修缮（现有） | 批次② |
| **道路** | 路况 | 移速倍率 | 变碎石路 / 消失 | 养护 | 批次② |
| **植物** | 生机（沿用 `Hp`） | 产果量、木材产出 | 枯死 | 闲置自愈（现有） | 批次③ |
| **动物** | 体况 | 繁育率、被捕价值 | 自然减员 | 无 | 批次③ |
| **人** | 健康（沿用 `Health`） | 劳动效率 | 死亡 | 无 | 批次③ |

房屋与植物**已各自实现过一根轴**（`Condition`、`Hp` + `IdleDays` 延迟回血），
批次②③的统一工作是改名、补另一根轴、把衰减器抽成公共的——工作量集中在货品与道路这两处从零开始的。

**道路的特殊约束**：`Cell` 是 struct、活在 100 万格的密集数组里（`MapGrid`），**不能加字段**。
道路状态必须走稀疏字典（只存有路的几千格），存档在 `MapSave` 加一组与 `RoadCells` 平行的列表。

### 已知待办与限制

- **配方系统不认识物品状态**：`Goods.Recipes` 按 `goodsId` 索引，不做状态条件判定。
  故「变质的粮拿去堆肥」目前只能通过硬轴降级为 `Scrap`（已是燃料类货品、天然可作他用）实现；
  要支持「鲜度 < 15 的粮食 → 肥料」需在批次④给配方加状态条件。
- **加工输入未按鲜度折算**：`CraftingSystem` 取原料走的是普通取出，陈粮酿酒与新粮同产率，待办。
- **搬运状态为近似**：跨批搬运时状态按取出量加权混合（单批场景精确无损）。
- 数值全部为初稿，尚未经试玩校准。
