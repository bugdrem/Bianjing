# 全代码 Review：可玩性评估与经济循环核算

> 审查时间：2026-10-24 ｜ 代码范围：`scripts/` 全量 121 个 `.cs` + `data/*.json` + `configs/`
> 方法：三个并行子代理分头审计（经济收支 / 可玩性与内容 / 反馈环与健壮性），交叉核验后合稿。
> 所有论断均附代码位置或可复算的算术；纯推测性内容已标注「待实测」。

---

## 0. 结论摘要

**经济：能正向循环，但是「官库主导的外循环」，不是「城市自持的内循环」。**
当前经济体量的正负取决于官库建筑的密度而非人口规模；城市自身（家庭↔铺面）的闭环不足以支撑人口增长，缺口的填补者始终是王爷月俸与朝廷粮饷这两笔外部注入。三处数值倒挂（铸币局净亏、商铺早期税负倒挂、口粮断链）与一个瓶颈（流民营 16 空位）限制了扩张速度，但**没有任何一条反馈环会自然死亡**——未发现必然硬锁。

**可玩性：这是当前最大的短板。模拟层已经"活着"，游戏层尚未"成形"。**
城市会自己长、自己吃、自己老、自己坏，但玩家没有目标、没有终局、没有失败条件、没有危机事件，开局引导只有王爷府里的一句话。**`DemandLedger` 驱动了全部 NPC 决策，却在注释里写着"暂不显示给玩家"——这是整条信息链上最大的断点**：玩家看不到自己城市缺什么，也就无从决策。

一句话：**《汴京盛卷》现在是一个合格的"城市模拟器内核"，还不是一个"游戏"。**

## 2. 经济能否正向循环

### 2.1 结论

**能转，但转的是官库，不是城市。**

钱在「外部注入 → 官库 → 村民家庭 → 铺面/工坊 → 回流官库」的闭环里流动。
问题是这个环的**起点与终点都是官库**：官库既是唯一的货币发动机（铸币局），又是唯一的兜底购买者（朝廷采购）与唯一的征税方。
城市内部（家庭↔铺面）的交易是零和的——铺面多收一文，家庭就少一文，不产生新的钱。

因此经济的正负，本质上等于：

```
官库净额 = 铸币收入 + 土地税 + 商税 + 王爷月俸 − 雇工俸禄 − 建筑维护 − 朝廷粮饷
```

### 2.2 官库净额的实测形态（子代理模拟，可复算）

| 情景 | 官库净额（文/月） |
|---|---|
| 20 人口（开局形态） | **+25,340** |
| 100 人口（建满 9 座官产） | **−14,700** |
| 400 人口（成熟城市） | **+169,700** |

**注意这个形态：净额不随人口线性增长，而是随"官产密度"起伏。**
100 人口反而不赚钱，是因为此阶段官产（铸币局/官田等）的固定成本（工资 + 维护）已经全额支出，但人口还没多到把税基铺开。
折算下来，**每位市民每月向官库贡献的税后回流约 550 文**——这就是"外部注入"以外城市自己产钱的能力。

> 关键读法：**官库在 400 人口时是赚钱的，说明正循环成立**；但 100 人口阶段的亏损说明——**从中期起步，玩家必须先垫一笔钱把人口养到税基铺开的规模**。这笔"过桥钱"来自开局安家银 100,000 文与王爷月俸。

### 2.3 家庭端：负担率

| 家庭形态 | 月收入 | 月支出（家计+口粮+税） | 负担率 | 月余 |
|---|---|---|---|---|
| 三口双职工 | ≈7,000 | ≈3,180 | **46.4%** | ≈4,820 |
| 务农组合 | ≈4,600 | ≈2,950 | **64%** | ≈1,650 |

46% 的负担率是健康的（有结余、有消费能力、但不至于快速致富）；64% 偏紧，但务农本就被设计成"稳但不赚"的保底职业。
**没有家庭会必然破产**——见 §4。

### 2.4 三重保底：为什么没人会归零

这是本次审查**最让人放心的发现**。无业/失业者有完全独立的三条收入通路：

1. **建筑维护费**（`EconomySystem.TickDay` → `PayBuildWages`，批次七十九）：官库每旬发的维护工钱直接发给当日无业者当营造杂役用工。**钱不是扣了消失，而是发出去又可能被税收回来。**
2. **营造工钱**（`GameState.PayBuildWages`）：玩家每盖一栋楼，工钱先发放、按实扣款，无人领则留在官库。
3. **朝廷采购**：凭空生成的购买需求。

三条通路互不依赖，因此**无业贫困不会螺旋下坠**。

### 2.5 三处数值倒挂（按严重度排序）

#### P0-① 铸币局：唯一的货币发动机，却是净亏项目

**算术**（`data/buildings.json` + `EconomySystem.MintCoins`）：

| 项 | 数值 | 依据 |
|---|---|---|
| 铸币收入 | 4 工匠 × `MintPerWorkerDay=150`/真实日 × 10 真实日/旬 × 3 旬 | = 18,000 文/月 |
| 工匠工资 | 4 × `salary=3000` | = 12,000 文/月 |
| 建筑维护 | `upkeep=10000` | = 10,000 文/月 |
| **净额** | 18,000 − 12,000 − 10,000 | **= −4,000 文/月** |

**满负荷运转的铸币局，是官库每月确定失血 4,000 文的项目。**
这意味着经济系统里唯一的"凭空造钱"装置是个漏卮——城市越依赖铸币，官库越穷。
（历史修正记录：批次九十六曾把 `mintPerWorkerDay` 从 50 改到 800，现值为 150，是"旬=10 真实日"新尺度（批次九十八）下重新定标的结果，但**没有同步复核工资与维护**，于是从"暴利"翻车到"亏损"，越过了平衡点。）

**建议**：`mintPerWorkerDay` 提到 220~250，使满负荷净额落在 +2,000~+5,000 文/月。货币发动机应当微利，不该微亏。

#### P0-② 商铺早期税负倒挂：商铺在早期是负资产

**算术**（`TaxSystem.BuildingTaxBase`）：

| 项 | 数值 |
|---|---|
| 商铺 L1 月土地税 | 3,000 文（`"shop" => level 1 => 3000`，默认税率 3% 档实收） |
| 审计测算早期商铺月毛利 | ≈ 2,450 文 |
| **店主净额** | **≈ −550 文/月** |

税基在批次九十五被整体放大了 6~10 倍、批次九十八又随新时间尺度 ×10，理由是"旧税基与物价完全脱节"（注释 `TaxSystem.cs:18-19`）。但放大只校准了"住宅 vs 一口粮"的比例，**没有校准"商铺税 vs 商铺毛利"**——商铺不是靠工资活的，它靠的是买卖差价，而早期商铺的差价根本盖不住 3,000 文的定额税。

**后果**：玩家早期建商铺是纯粹的财政自杀；而商铺又是城市商业层的唯一入口。
**建议**：商铺 L1 税基降到 1,500 文，或改为"定额税 + 营业额比例税"的复合制（后者更符合历史，也更能随城市成长自动缩放）。

#### P1-③ 口粮供应断链： grain 没有官营直售入口

`EconomySystem.PayMonthlySalary` 的朝廷粮饷是按 `CourtFoodCapPerCapita` 封顶拨入官仓的（批次八十七的修正），而官仓只赈济、不零售。
农户产粮 → 但**商铺默认不收粮**（grain 不在商铺收购清单）→ 家庭零买只能靠铺面 → **城中有粮、市民买不到粮**。

这是"官仓上限"修正时没同步修的断链：上限堵住了官粮无限膨胀，却也堵死了 grain 流入市场的正规渠道。
**建议**：允许官营粮店（或任一商铺的粮食专柜）按 `BuyerPrice` 收粮，让官仓成为市场调节者而非绝缘体。

#### P1-④ 死配置：`SettlementGrant = 1,000,000` vs `StartMoney = 100,000`

`EconomyConfig.cs:15` 的 `SettlementGrant` 是 `1_000_000`，而 `WorldConfig.cs:56` 的 `StartMoney` 是 `100_000`，
两者的注释却互相声称"安家银值匹配"（`PrinceMansionConfig.cs:18` / `WorldConfig.cs:55`）。
实际生效的是 `StartMoney`；`SettlementGrant` 无人读取，是**差 10 倍的误导性死常量**。
**建议**：删掉 `SettlementGrant`，或让 `StartMoney` 直接引用它，只留一个真值。

### 2.6 飞轮最紧的一环

**流民营只有 16 个空位**（`data/buildings.json` `"refugee_camp" ... "capacity": 16`），
而迁入必须有可寄居处才成行（`LifecycleSystem.Immigration`，`scripts/citizens/LifecycleSystem.cs:157-171`）：

```csharp
var host = FindLodging(gs);
if (host == null)
{
    gs.PostNews("migrate-in", "流民欲入城安置，但城中尚无流民营可接纳（建设「流民营」后迁入者抵达）");
    return;
}
```

**没有流民营 → 迁入永久停滞**（只在公告栏留一句提示，玩家极易漏掉）。
而流民又是后续自建民居、税基铺开的唯一人口来源。
**这是"开局 20 人 → 100 人"这一段最难跨的坡**：建流民营 → 等迁入 → 划坊区给自建 → 才有人口税基。

**建议**：① 开局引导必须包含"建流民营"这一步（见 §3.3）；② 流民营容量 16 在 400 人口目标下明显偏小，可改为按等级 16/32/64。

## 3. 可玩性评估

### 3.1 结论

**模拟活着，游戏未成形。** 底层模拟的完成度相当高（见 §4），但"游戏"所需的五件套——**目标、终局、失败、危机、引导**——一件都没有。

具体的玩家体验曲线：

```
0~5 分钟   盖王府、看地形、摆第一栋民居 —— 有反馈（建筑立起来、村民入驻）
5~15 分钟  建农田、建工坊、看人口爬到 30~50 —— 有反馈（数字在涨）
15~30 分钟 该建的都建了，人口自己长，钱自己转 —— 反馈开始稀释
30 分钟后  「看着城市自己长」—— 无事可做
```

**30 分钟后玩家进入纯观看状态**，这是可玩性评估的核心结论。

### 3.2 缺失的目标层

| 应有 | 现状 |
|---|---|
| 明确目标 | 无。只有"把城建大"这一模糊方向 |
| 终局/胜利 | 无。里程碑最高到「京城」即封顶，无通关概念 |
| 失败条件 | 无。官库可无限负（见 §4.4），人口不会归零，无破产/覆灭 |
| 危机事件 | 无。瘟疫、灾害、火灾、外敌、特产竞争均不存在 |
| 任务链 | 有框架但是死常量（朝廷赏赐/任务未接真数据） |
| 成就/里程碑反馈 | 有，但拨款 150~3000 文相对建筑造价"无感"——里程碑完成了，玩家毫无获得感 |

**最刺眼的一条**：里程碑拨款 150~3,000 文，而一栋铸币局造价 600,000 文（`data/buildings.json`）。
里程碑奖励与造价差 2~3 个数量级，等于没有奖励。

### 3.3 最大的信息断点：DemandLedger 对玩家不可见

`scripts/sim/DemandLedger.cs:7` 的类注释原文：

> 「中央需求账本（第 9 项·阶段一）：城市级供需统计，作为全局可查阅的被动参考（**上帝视角，暂不显示给玩家**）。」

而这个账本**驱动了全部 NPC 决策**——择业、建田、产业规划，NPC 都在查它（注释第 8 行：「NPC 在各决策点主动查阅账本据此抉择」）。

**后果是双重失真：**

1. **玩家侧**：看不到城里缺什么、余什么。玩家想"我该建个磨坊吗？"，游戏知道答案但不告诉他。
2. **NPC 侧**：NPC 能看见玩家的城市，玩家看不见 NPC 看见的东西——**玩家是全场唯一的信息盲人**。

这是整条链上**性价比最高的一个修复**：账本已经算好了（`DailyDemand` / `Stock` / `DaysOfStock` / `IsShort` 四个字段全都在），
缺的只是一个面板。一个「供需」面板就能把 30 分钟后的无事可做状态直接改写成"缺粮 → 建官田 → 观察库存回血"的决策循环。

**建议（P0）**：做「城市供需」面板，直接渲染 `DemandLedger.Entries`，缺货（`IsShort`）标红。

### 3.4 开局引导断崖

开局引导的全部内容是**王爷府建筑上的一句话**。
而 §2.6 说过，飞轮最紧的一环是"建流民营 → 等迁入 → 划坊区"。
**玩家在没有任何提示的情况下，极可能永远不建流民营**（因为不知道它存在），于是迁入永久停滞，人口锁在开局规模——这不是玩家失误，是引导缺失。

**建议（P0）**：把引导改成 3~4 步的轻量任务链，正好复用已有的任务框架：
1. 建流民营（解锁人口流入）
2. 划坊区（解锁自建民居）
3. 建官田/磨坊（解决口粮）
4. 达成都城 milestone（第一次正向反馈）

### 3.5 已经具备的底子（不要重复造）

评估时要公平：以下系统**已经真实实现且质量不错**，缺的只是"把它们串成游戏"的那层皮。

- 互市/外贸（`visitors/`：ForeignVisitor/Stall/VisitorSystem/WalkerPathfinder）
- 物品时效双轴系统（四批完成，含翻新/ Salvage /环境修正接口）
- 政策/财政/科技三套可调系统（税率、俸禄、科技加成都在生效）
- 骨骼村民 + 4 段动画 + glb 资产管线（树/动物）
- 公告栏播报（`PostNews`）——**任务链的天然载体，已经存在却没被任务系统用上**

## 4. 健壮性：反馈环会不会死

这是审查中**结论最清晰、最乐观**的部分。

### 4.1 饥饿螺旋 —— 不会死

三重刹车，缺一不可，而三者在场：

1. **100% 转 Logger**：饥饿不会直接致死，而是降劳动岗位类型
2. **LaborFactor 下限 0.35**（`LifeConfig`）：再饿也保留 35% 劳动力，不会归零
3. **健康回复**：`Citizen.Health` 已真实接入（此前的恒 100 死字段已修复），温饱即回血

### 4.2 就业贫困螺旋 —— 不会死

**83% 转 Logger 安全阀**：求职失败者绝大多数退回樵夫/杂役等基础岗位，而非滞留失业。
且扣款路径全部"见底即止"（`TakeFromFamily` 实扣、不足少收），不会出现负资产追杀。

### 4.3 建筑衰减维护 —— 不会死

衰减 → 重建是一个**循环而非崩塌**：维护费本身发给无业者（§2.4），修缮匠与住户集资两条回滚通路都在。
刻意不拆道路（只降级）保护了玩家的路网投资。

### 4.4 财政螺旋 —— 条件性软锁（唯一需要关注的一条）

`EconomySystem.PayWages`（`scripts/sim/EconomySystem.cs:72-76`）：

```csharp
if (total > 0)
{
    gs.Money -= total;      // ← 无下限，无"付不起停发"闸门
    gs.Ledger.Add("雇工俸禄", -total);
}
```

**工资月结没有"官库付不起就停发"的闸门**，官库可以无限负数运行。
但这不是硬锁，原因有二：

1. **月俸是恒定的**，不随官库余额变化，所以不存在"越欠越多"的利息式恶化；
2. **可拆楼还债**——拆建筑回收成本，玩家有明确的脱困操作。

**判定：条件性软锁，非必然硬锁。**
**建议（P2）**：加一条闸门——官库为负时雇工俸禄打折发放（如 70%），既保留压力又不破坏可解性。

### 4.5 工程健壮性

- 存档：线程安全，无字典枚举中修改，无裸除零
- 存档版本：`FormatVersion` 刻意不升（新字段均有安全默认值，旧档读入即"万物如新"）——符合早期开发约定
- `MathF.Clamp` 误用、`const bool` 折叠等已知坑均未复发

## 6. 一页结论

**经济**：能正向循环。400 人口时官库 +169,700 文/月，每位市民贡献约 550 文税后回流；
家庭负担率 46%（双职工）~64%（务农），无人必然破产。但它是**官库主导的外循环**，
且有三处数值倒挂（铸币局 −4,000/月、商铺早期净亏、口粮断链）和一个扩张瓶颈（流民营 16 空位）。

**可玩性**：**最大的短板。** 模拟层活着，游戏层缺席——无目标、无终局、无失败、无危机、引导只有一句话。
而破局点异常清晰：**账本已经算好了一切，只差一个面板；公告栏已经能播报，只差一条任务链。**
把 P0 的四项做完，《汴京盛卷》就从"城市模拟器内核"变成"能玩的城市营造游戏"。

**健壮性**：三条社会反馈环均有多重刹车，未发现必然硬锁；唯一需要关注的是财政软锁（无停发闸门），
但月俸恒定 + 可拆楼还债使其保持可解。
